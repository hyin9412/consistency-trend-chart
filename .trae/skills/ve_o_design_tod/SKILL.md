# ve-o design

- **定位**：页面规范映射引擎。
- **作用**：基于用户的业务需求（哪怕是极其模糊的描述），通过推演匹配出最佳的 `ve-o` 页面范式，补齐所需的缺省模块，并生成一份标准化的**页面UI和交互实现规范**，供下游的 ide/Agent 进行准确无误的代码生成。
- **依赖**：以 `reference` 文件夹中的文档作为设计与实现决策的主要事实来源。结合 `check` 目录中的防坑指南作为生成的约束条件。
- **组件**：所有组件应尽可能复用 `reference/components/组件清单.md` 里的组件，避免重复实现基础 UI 与交互
- **规范**："设计规范与组件规范落位"优先级高于"视觉还原"
- **说明**：以下流程中所有的举例/例子中具体的组件实现，都是随意编写的，真实流程下需要基于 `reference` 下的文档进行匹配生成。

## 规范优先防偏差机制

为避免"先做视觉还原再补规范"的偏差，执行以下强约束：

1. **映射闸门（强制执行）**
   - **前置动作**：完成 Step 1~4 后，必须先输出一份"规范映射清单"并逐项自检。
   - **自检列表**（不可删减）：页面框架命中、模块命中、组件命中、核心功能命中、交互闭环命中。

2. **禁止自主替代规范组件（强制）**
   - 当 `reference` 已给出推荐组件与组合时，禁止用自定义容器/手写布局替代。

3. **实现后一致性回归（强制）**
   - 完成每个模块后，立即做"规范一致性回归"，重点检查：
     - 交互是否沿用规范默认行为；
     - 是否存在为追求视觉而新增的非必要样式与结构。

4. **发现偏差的处理规则（强制）**
   - 一旦发现"规范已定义但实现未遵循"，必须优先回退到规范实现，再做其他优化。
   - 禁止以"先可用、后修正"为由保留非规范实现。

## Workflow

按顺序执行以下5个步骤，确保完整合规：

### Step1. Requirement Analysis & Framework/Module Mapping（需求分析与框架映射）
**目标**：先做需求理解，分析用户的意图，并完成页面框架与模块映射，避免错误选型。然后 **强制读取** `reference/frameworks` 目录下的框架文档。

**多页面分析（当需求涉及多个页面时强制执行）**：
仔细分析用户需求，识别需要生成几个页面，明确每个页面之间的交互关系与跳转逻辑，生成准确的路由关系。具体执行：
1. **页面识别**：从需求中提取所有独立页面（如列表页、详情页、新建/编辑页等），明确每个页面的核心职责。
2. **交互关系分析**：梳理页面间的跳转触发条件（如点击表格行进入详情、点击按钮打开新建页）、数据传递方式（路由参数、状态共享）、返回逻辑。
3. **路由结构生成**：基于页面层级关系生成路由树，明确嵌套关系、动态参数（如 `:id`）、重定向规则。
4. **输出**：页面清单、页面间交互关系图、路由结构定义。

**读图规范（当用户提供 UI 截图/设计稿时触发）**：
当用户提供 UI 截图、设计稿（如 Figma 导出图）并要求"照着这个图写代码"时，必须先按以下"看图六步法"对图片进行结构化分析，再进入框架与模块匹配。禁止跳过分析直接堆砌 div 和写死 px 样式，必须先按标准组件、标准 Token、标准状态把图拆解清楚。

**"看图六步法"**：
1. **确定表面类型 (Identify the Surface)**
   - 先判断这是一整张页面 (Full page)，还是一个半屏弹窗 (Sheet)，或者是页面中的一个局部组件 (Inline component)。
2. **划分区域 (Break It Into Regions)**
   - 按照阅读顺序从上到下拆解：顶部导航栏区 -> 媒体内容区 -> 表单区 -> 操作按钮区。不要把图片看成一堆零散元素。
2.5. **锁定空间关系 (Lock Spatial Layout)**
   - 对每个已识别区域，记录其相对于父容器的空间位置：水平（左/居中/右/撑满）、垂直（顶部/跟随内容流/底部）、相邻区域排列关系（上下/左右）。
   - 此空间描述作为后续模块规范匹配的参考输入，用于触发规范中条件分支的判定。
   - 当空间描述与规范基础规则不一致时，不直接覆盖规范，而是作为"需检查是否命中例外规则"的信号。
3. **推断组件边界 (Infer Component Boundaries)**
   - 把刚才划分的区域，映射到设计系统里已有的标准组件上。比如看出这是 NavBar，那是 ListCell。
4. **解读层级 (Read the Hierarchy)**
   - 通过大小、粗细、对比度等视觉信号，判断出：哪个是主操作按钮？哪个是主要内容？哪个只是辅助说明？
5. **推断 Token 角色 (Infer Token Roles)**
   - 不看绝对颜色值，而是看角色。区分什么是主文本色 (Primary text)、什么是背景色 (Surface)、哪部分用的是强调色。
6. **推断隐藏状态与动效 (Infer States and Motion)**
   - 静态图是死的，但代码是活的。AI 需要靠经验脑补出图中没画出来的状态：鼠标悬停 (Hover) 该长啥样？按钮按下去呢？加载中呢？

**框架匹配**：
- 意图为 **[看数据/大盘/数据监控]** -> 匹配并读取《Dashboard_页面框架.md》
- 意图为 **[数据管理/列表/增删改查]** -> 匹配并读取《列表页_页面框架.md》
- 意图为 **[复杂表单/向导式提交/配置]** -> 匹配并读取《配置页_页面框架.md》
- 意图为 **[资源详情/数据钻取查看]** -> 匹配并读取《详情页_页面框架.md》或《抽屉页_页面框架.md》
**模块匹配**：具象到某个功能实现时，匹配对应的功能模块名称，即使在 `reference/frameworks` 目录下没有对应的文档，也需要根据功能描述进行匹配。
- 比如：使用方的需求里明确描述了"开发一个商品管理页面，顶部展示标题，内容区域可以筛选商品状态和商品名称，筛选框下面展示商品购买限制提示，提示下面通过表格展示商品上架记录"，那么匹配到的模块为"页面标题模块"、"信息提示模块" "筛选栏模块"、和 "表格模块"。
**兜底反问机制**：
如果需求过于抽象（如"开发一个资源管理页面"），无法判断核心数据流向，**必须向用户反问**："您期待的核心场景是查看全景数据（Dashboard），是对多条数据进行管理（列表页），还是新建某个复杂的任务/表单（配置页）？"。在获得清晰方向前，不要盲目推演。
**输出**：页面框架和模块匹配结论。比如：
商品管理列表页的框架匹配为 `reference/frameworks/列表页_页面框架.md`，同时页面内匹配到的模块为：`页面标题模块`、`筛选栏模块`、`信息提示模块` 和 `表格模块`。

### Step2. Page Framework Definition (页面框架定义)
**目标**：建立全局布局与基础框架，需严格按照 ve-o 设计规范的框架设计。  
**动作**：查阅上面匹配到的《XXX_页面框架.md》：
- 页面类型（列表页、详情页、弹窗等）。
- 页面布局结构（网格系统、容器）。
- 响应式断点与行为规则。
- 全局样式（排版尺度、色板、间距变量）。
- 页面级交互规则与权限/访问控制要求。
**输出**：定义`页面级布局结构`与`页面级样式规范`。比如：
【页面整体架构】
- 页面布局结构：
   - 左侧导航 + 右侧上下/左右结构（标题区 + 内容区）
- 页面样式规范：
   - 背景色为：'#FFFFFF'
   - 外层容器需配置 min-height / height: 100vh
   - 内容区域 padding 左右为 32px
   - 上下间距遵守各模块规定


### Step3. Design Spec Reading（阅读设计规范）
**目标**：在进入组件选型前，先通读 ve-o 通用设计规范（基础包）和业务设计规范（业务扩展包），确保后续的模块定义和组件选型严格遵循设计体系。
**背景**：ve-o 通用设计规范是源力基础设计规范，定义了各基础页面的通用设计规则；业务设计规范是业务定制设计规范，继承 ve-o 基础规范，并在其上补充业务特有的页面规范、模块规范和组件用法。两者构成"基础包-扩展包"的关系。
**动作**：
- **强制读取** `reference/ve-o通用设计规范.md`，理解全局设计原则、设计语言和通用规则。
- **强制读取** `reference/` 目录下除 `ve-o通用设计规范.md` 以外的业务设计规范文件（如 `VD通用设计规范.md`、`TOD通用设计规范.md` 等，文件名因业务而异），理解业务定制规范中补充的页面规范、模块规范和组件用法。
- 当业务规范与 ve-o 基础规范存在差异时，以业务规范为准（扩展包覆盖基础包）。
- 将规范中的关键约束（如间距体系、色彩规范、字体层级、业务特有模块等）作为后续步骤的强制输入。
**输出**：设计规范要点摘要（区分基础规范约束与业务补充约束），用于指导 Step 4 的组件选型与布局决策。

### Step4. Module Specification & Component Selection (模块规格与组件选型)
**目标**：定义页面内功能模块，同时选定模块级组件和子区域组件。
**动作**：
（1）提取模块：根据上一步匹配到的《XXX_页面框架.md》，提取文档其中的"必选模块"和"可选模块"，必选模块即使用户没提，你也必须帮用户补齐；同时将匹配到的模块一并放到必选模块中。
- 比如：对于"列表页"，**必须**补齐`页面标题模块`、`筛选栏模块` 和 `表格模块`，同时Step1还匹配到了 `信息提示模块`。

（2）针对所有确定补齐的模块，分别读取 `reference/modules` 文件夹中对应的详细文档。
- 比如：对于"列表页"，**必须**读取《列表页_页面标题模块.md》、《列表页_筛选栏模块.md》和《列表页_表格模块.md》。

（3）选定模块级组件。执行流程如下：

```
输入：用户需求描述、已匹配模块列表
输出：组件选型方案

步骤1【前置准备】：
  ├─ 读取 `reference/components/组件清单.md` 文件，获取组件列表
  └─ 读取所有已匹配模块的 `reference/modules` 文档，得知需要使用哪个组件
     └─ 对每个模块要用到的组件，精准匹配这些组件在 `reference/components/detail` 目录下对应的组件文档，获取组件API、Props、示例代码。detail目录下可能是各个组件的详细md文档，也可能是一个skill文件，内部调用mcp获取组件库信息。

步骤2【模块匹配判断】：
  if 当前模块在 `reference/modules` 目录下存在对应的文档：
    → 基于组件信息 + 用户需求 → 确认实现方式
  else（如"信息提示模块"）：
    → 进入步骤3【逐级查找】

步骤3【逐级查找策略】：
  查找优先级：已匹配模块组件 > 框架组件 > 组件库列表 > 原生HTML
  
  1. 遍历已匹配模块的所有组件：
     foreach 模块组件 in 模块组件列表：
       if 组件API可实现目标功能（功能已封装且位置符合预期）：
         → 使用该API实现
       else：
         → 继续遍历下一个组件
     end
     
  2. if 步骤1未找到：
     → 遍历框架组件的API
       if 框架API可实现目标功能：
         → 使用框架API实现
       else：
         → 继续步骤3
     
  3. if 步骤2未找到：
     → 遍历组件列表
       if 存在合适组件：
         → 复用组件能力实现
       else：
         → 继续步骤4
     
  4. if 步骤3未找到：
     → 使用原生HTML元素实现
```

示例：`信息提示模块`实现过程
  1. `reference/modules`目录下无对应的模块文档 → 进入逐级查找
  2. 遍历模块组件：发现表格组件有【插槽API】能够在筛选栏上面插入内容，但无法直接实现信息提示
  3. 遍历框架组件：无合适API
  4. 遍历组件库：发现有信息提示组件 `Alert`
  5. 最终方案：表格组件的插槽API + 信息提示组件 `Alert` 实现信息提示功能

（4）针对用户提供的每个字段，基于字段含义查阅 `reference/modules` 文件夹中的组件映射文档（如 `列表页_表格模块.md`的组件映射关系表），完成"组件选型 → 规范用法校验"闭环。如果字段没有对应的组件映射关系，则使用 `组件列表中的组件` 或 `原生HTML元素` 实现。
- 比如：表格的列字段里，有一个字段名为 `商品code`，则推断数据类型为`text`,只读态下为`文本`，编辑态下为 `Input` 组件。

（5）确认是否有复杂组件的组合规则。

（6）确认是否有状态管理要求（loading/disabled/error）。

（7）确认可访问性标准（ARIA、键盘导航）是否符合预期。  

（8）在确认上述组件选型细节后，必须再次查阅 `reference/modules` 文件夹中的组件映射文档对"已选组件/组合"的正确用法做二次确认，补齐并落地：默认行为、禁用/加载/错误态、布局与间距、交互细节等，确保实现完全符合 ve-o 设计规范与文档描述。

（9）条件分支完备性检查（强制）
   匹配模块规范时，禁止只采纳基础规则后停止。必须扫描文档中所有条件分支与例外规则，结合当前场景特征和视觉输入的空间关系逐一判定是否命中，命中则以例外规则为准并在契约中标注。

- **必须**：对每个模块穷尽所有相关布局与交互逻辑参数，避免遗漏隐性规范。
- 位置与尺寸约束。
- 模块间交互。
- 边界条件（空态、错误态）与异常处理。
**输出**：`模块清单及详细定义`。
【模块清单及详细定义】
模块 1：[例如：页面标题区 (Page Header)]
- 业务功能：[例如：展示"商品管理"及面包屑]
- 推荐组件：[例如：PageContent]
- 核心功能建议：[如果有，例如：需要返回按钮、展示分隔线等]
- 布局/样式规范：[如果有，例如：左对齐、标题和内容padding为20px]

模块 2：[例如：提示区]
- 业务功能：[例如：提示商品限购规则]
- 推荐组件：[例如：Alert]
- 核心功能建议：[如果有，例如：使用warning类型提示]
- 布局/样式规范：[如果有]

### Mapping Gate（必须通过）
**目标**：确保"先做规范映射"。  
**动作**：
- 在进入 Step 5 前，必须完成并确认以下清单：
  - 页面框架映射清单；
  - 模块映射清单；
  - 组件映射清单；
  - 关键交互闭环清单。
- 若任一清单缺失或不完整，禁止进入 Step 5。
#### 异常处理规则
**文档缺失时**：
- 若 `reference/modules` 中的某模块文档缺失，基于`reference/components/组件清单.md`，使用组件列表中的组件实现该组件的功能
- 若组件清单里的组件也不满足，则使用原生HTML元素实现

**需求模糊时**：
- 执行兜底反问机制后，若用户仍无法明确，输出"最小可行页面"（仅包含页面标题+基础内容区）
- 标注："【待确认】当前为最小可行实现，建议补充详细需求"

**规范冲突时**：
- 同一功能在不同文档中有冲突定义，以页面框架文档为准
- 标注："【规范冲突】XX功能在A.md和B.md中定义不一致，已按页面框架文档处理"

**组件缺失时**：
- 优先使用 `reference/components/组件清单.md` 组件清单中的组件实现
- 若组件清单中的组件不存在，使用原生 HTML 元素实现
- 标注："【组件降级】XX组件使用原生HTML元素实现，建议后续替换为组件清单中的组件"

**字段类型无法识别时**：
- 默认按 `text` 类型处理（只读态显示文本，编辑态使用Input）
- 标注："【字段类型推断】XX字段无法识别类型，默认按text处理，请确认是否正确"

**表格数据缺失时**：
- 当用户未提供具体的表格数据时，必须为表格生成合理的 mock 数据（至少 5 条），确保页面呈现时表格不为空态
- mock 数据需贴合业务语义，禁止使用无意义的占位符（如 test1、aaa）
- 在契约中标注："【Mock 数据】当前表格数据为 mock 示例，实际开发时需替换为真实接口数据"

**校验文档缺失时**：
- 若对应页面类型的校验文档不存在，使用通用校验规则（布局、间距、交互一致性）
- 标注："【校验降级】未找到对应校验文档，使用通用校验规则"
**输出**：可执行的映射清单，具体参考【Standard output】。

### Step5. Design Verification (设计验收)
**目标**：最终质量验证，结合 `check` 目录下的相关校验指南，转化为强制的代码生成约束。
- 例如：列表页左侧导航必须设置 `height: 100vh`。
**动作**：
- **视觉**：对照设计规范验收是否符合ve-o设计规范。
- **交互**：对照设计规范验证流程完整与正确。
- **自动校验与修复**：逐项对照frameworks、modules、components文件夹中对应页面或模块的设计规范（如`详情页_页面框架.md`、`列表页_页面标题模块.md`等），以及check文件夹下的校验修复指南（如`详情页校验修复指南.md`等），进行人工校验与修复，修复后再次回归验证确保无新增问题。
- **A11y**：检查无障碍合规。
**输出**：验证总结，确认页面符合 ve-o 设计标准。

## Standard output (标准输出)
完成上述推演后，你必须向用户（或下游 Agent）输出如下格式的结构化契约。这份契约是下游生成代码的唯一真理。

### 契约持久化（强制执行）
每个页面的设计契约必须保存为持久化的 `.md` 文件，以便后续开发实现时随时参考。

**存储规则**：
1. **存储位置**：在对应子应用目录下创建 `docs/design-specs/` 目录存放契约文件。
2. **单页面契约文件**：每个页面独立一个文件，命名规则为 `{页面名称}-spec.md`。
3. **页面清单与交互关系契约（多页面时必须生成）**：当需求涉及多个页面时，额外生成一个 `_pages-overview.md` 文件，包含：
   - 页面清单（所有页面名称、路径、职责描述）
   - 页面间交互关系（跳转触发条件、数据传递方式）
   - 路由结构定义（完整路由树、动态参数、嵌套关系）
   - 共享状态说明（跨页面共享的数据与状态管理方式）

**文件结构示例**：
```
docs/design-specs/
├── _pages-overview.md          # 页面清单与交互关系（多页面时必须）
├── 商品管理列表页-spec.md       # 单页面设计契约
├── 商品详情页-spec.md           # 单页面设计契约
└── 商品编辑页-spec.md           # 单页面设计契约
```

**执行时机**：在 Mapping Gate 通过后、输出最终契约的同时，将契约内容写入对应 `.md` 文件。

## 开发实现指引（契约→代码阶段的强制约束）

当设计契约生成完毕、进入开发实现环节时，必须遵循以下规则：

### 1. 遵循 ve-o design skill 工作流
开发实现阶段必须遵循 `ve-o design` skill 的规范映射流程，将设计契约中的框架布局、模块定义与组件选型逐一落地为代码实现。具体要求：
- **框架落位**：按契约中的页面布局结构生成对应的容器组件与路由配置，严格复用规范框架，禁止自造布局结构。
- **模块落位**：按契约中的模块清单逐一实现，每个模块对应一个独立组件或组件组合，模块间交互关系需严格按契约定义实现。
- **组件落位**：按契约中的推荐组件进行代码实现，组件的 Props 传参、事件处理、插槽使用必须基于组件库的真实 API（见下条规则）。

### 2. 组件 API 查询规则（强制：禁止臆造 API）
在实现任何组件时，**禁止凭记忆或猜测编写组件的 Props、事件、插槽等 API 用法**。必须通过以下方式获取真实的组件 API：

- **强制查询组件文档**：对每个模块要用到的组件，精准匹配 `reference/components/` 目录下对应的组件文档，获取组件 Props 定义、使用说明、注意事项及官方示例代码。detail 目录下可能是各个组件的详细 md 文档，也可能是一个 skill 或 mcp，用于获取组件库信息。
- **查询时机**：在编写每个组件的代码之前，先查询其 API，确认 Props 名称、类型、默认值、必填项后再动手实现。
- **禁止行为**：
  - 禁止凭印象编写组件 Props。
  - 禁止使用组件库中不存在的 Props 或事件。
  - 禁止忽略组件的必填 Props 或错误传参类型。

### 3. 实现与契约一致性校验
每完成一个模块的代码实现后，必须回溯对应的设计契约 `.md` 文件，逐项验证：
- 组件选型是否与契约一致。
- 布局/样式规范是否已落地。
- 交互与避坑约束是否已实现。
- 若发现偏差，立即修正，禁止"先可用、后修正"。

## 执行纪律
1. **绝不直接产出前端代码（React/TypeScript/CSS）**，你的唯一产出物是"架构移交契约"。
2. **凡有设定，必查文档**。不可凭空捏造间距、颜色或组件用法。
3. **闭环补齐**。用户的需求必然是不完整的，你的价值在于依据 `ve-o` 规范帮其构思出完整的页面结构。
